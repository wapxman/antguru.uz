# ADR 0004: Ключевые решения схемы БД

**Дата:** 2026-04-18
**Статус:** принято

## 1. Пользователь может быть и клиентом, и специалистом

**Решение:** `User.roles UserRole[]` + отдельная таблица `SpecialistProfile` (1-1 с `User`, опциональная).

**Причины:**
- Единая учётная запись, один номер телефона, одни уведомления. Пользователь не делает "второй аккаунт".
- Базовый `User` чистый — нет кучи нуляемых полей типа `bio`, `rating`, `balance`, которые актуальны только для специалистов.
- Активация режима специалиста = создать `SpecialistProfile` + добавить `SPECIALIST` в `roles`.
- Авторизация проверяет наличие роли в массиве.

**Альтернативы:**
- Тип пользователя (`type: CLIENT | SPECIALIST`) — не даёт одновременности.
- Всё на одном `User` с nullable-полями — неопрятно и плохо масштабируется.

## 2. Деньги в BigInt (тийинах)

**Решение:** все денежные поля — `BigInt`, в минорных единицах (тийинах). 1 UZS = 100 тийин. Имя поля заканчивается на `Minor` — `budgetMinor`, `balanceMinor`.

**Причины:**
- Целочисленная арифметика — нет ошибок с float.
- `Int` (int32) мало для крупных сумм: 21M UZS = 2.1млрд тийин — уже упираемся в потолок.
- `Decimal` — вариант, но сложнее в JS (приходит как класс Prisma.Decimal, нужны преобразования).
- При сериализации в JSON на границе API — конвертируем `bigint → string`.

## 3. Двунаправленные отзывы

**Решение:** `Review` имеет `authorId` и `targetId` (оба — `User`), уникальность по `[orderId, authorId]`.

**Причины:**
- Клиент оценивает специалиста, специалист может оценить клиента (важно для исполнителя: плохой клиент — трата времени).
- Универсальная модель проще, чем две отдельных таблицы.

## 4. Чат привязан к заказу

**Решение:** `ChatThread` 1-1 с `Order`. Участники неявно: `order.clientId` и `order.selectedSpecialist.userId`.

**Причины:**
- Упрощает доступность и аудит: переписка всегда имеет контекст заказа.
- Не нужна свободная переписка на первом этапе — profi.ru-модель.
- При необходимости легко добавить `dmThread` между произвольными пользователями позже.

## 5. Путевые записи платежей в одной таблице

**Решение:** `Payment` хранит все типы операций (`TOPUP`, `WITHDRAWAL`, `RESPONSE_FEE`, `COMMISSION`, `REFUND`), направление — через `type`, сумма всегда положительная.

**Причины:**
- Единый аудит финансового движения.
- Провайдер-агностично: внешние (Payme, Click) и внутренние (INTERNAL) унифицированы.
- Баланс специалиста (`SpecialistProfile.balanceMinor`) — агрегат, обновляется в транзакции вместе с вставкой Payment.
