# ADR 0002: NestJS как бэкенд вместо Next.js API routes

**Дата:** 2026-04-18
**Статус:** принято

## Контекст

Бэкенд маркетплейса содержит много фоновой логики: платежи, очереди SMS/email, воркеры модерации, вебхуки от Payme/Click, cron-задачи. Next.js API routes плохо подходят для такого.

## Решение

Выделяем бэкенд в отдельное приложение **`apps/api` на NestJS**.

## Причины

- **Модульность из коробки.** Каждая фича — отдельный `@Module()` со своими контроллерами, сервисами, DTO. Это идеально для разработки с ИИ-агентами: модуль читается и правится изолированно.
- **DI-контейнер.** Чистые зависимости, легко мокать в тестах.
- **Встроенная поддержка** очередей (BullMQ), вебхуков, cron (`@nestjs/schedule`), WebSocket.
- **Guards / Interceptors / Pipes** — стандартный способ делать авторизацию и валидацию без изобретений.
- **Можно вынести в отдельный сервис** или разделить на микросервисы без переписывания.

## Альтернативы

- **Next.js API routes** — быстрее стартовать, но при росте фоновой логики всё превращается в кашу.
- **Fastify / Express напрямую** — нет встроенной модульности, пришлось бы изобретать.
- **Hono / Elysia** — современно, но меньше экосистема, меньше готовых решений для платежей и очередей.
